# 2026-09-15

- 집계 리포트는 이름·분류 같은 가변 속성이 아니라 불변 식별자(ID)로 그룹핑한다. 훈련명/영역을 키로 쓰면 마스터 데이터가 바뀐 뒤 같은 대상이 여러 행으로 쪼개지거나 목록에서 누락된다.
- 과거 기록을 보여줄 때 "기록 시점 값"과 "현재 값" 중 무엇을 쓸지 정책을 한 번에 정한다. 상세·요약·제목이 서로 다른 기준을 쓰면 같은 화면 안에서 숫자와 라벨이 어긋난다. 소급 표시로 통일하려면 조회 계층 전체를 같이 고쳐야 함.
- 주간·월간 요약은 별도 집계 테이블이 아니라 일간 원장 기록에서 재계산해야 상세와 합이 맞는다. 상위 집계를 따로 저장하면 이중 소스가 되어 드리프트 발생.
- 공용 리소스 풀(소속 없는 전역 데이터)은 조회 지점마다 필터에서 빠지기 쉽다. 목록·분석·즐겨찾기 등 유사 쿼리가 흩어져 있으면 같은 누락 버그가 반복되므로 조건을 공통 스펙/QueryDSL predicate 로 뽑아 재사용한다.
- 표준 분류 코드 태깅 기능은 태깅 값 자체와 변경 이력을 분리 저장한다. 현재 상태만 갖고 있으면 "언제 누가 왜 분류를 바꿨나"를 복원할 수 없고, 소급 집계 정책을 검증할 근거도 사라진다.
- 프론트에서 걷어낸 설정 필드는 백엔드 도메인·DTO 에서도 같이 제거하되, 컬럼 DROP 전에 NOT NULL 제약 해제를 선행한다. 배포 중 구버전 코드가 값을 안 넣어도 INSERT 가 깨지지 않는다.
- 순차 번호 기반 마이그레이션(Flyway 등)은 브랜치를 병렬로 따면 버전이 충돌한다. 머지 직전 최신 번호 확인 후 재넘버링하는 습관이 필요.
- QA 전용 확인 화면을 기능과 같은 티켓에서 함께 만들면 검증 비용이 크게 준다. 특히 이력·태깅처럼 DB 를 직접 봐야 확인되는 기능에 효과적.
