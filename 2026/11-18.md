# 2026-11-18

- 이력성 데이터(검사 결과 등)는 덮어쓰지 않고 누적 저장해야 시점별 변화를 추적할 수 있다. 관리자 API에서 이력을 조회하고 추가할 수 있게 둔다.
- dev·stg 환경에서만 고정 인증번호를 켜 두면 QA 때 실제 메시지를 받지 않고도 인증 흐름을 반복해서 테스트할 수 있다. 프로필별 설정으로 분리해 운영 환경에는 절대 적용되지 않게 한다.
- 정렬 키 문자열(`created` 등)이 매핑에 없으면 엉뚱한 기본 정렬(이름 내림차순 등)로 조용히 떨어질 수 있다. 정렬 키와 실제 컬럼의 매핑을 명시하고, 기본값을 테스트로 고정한다.
- 정렬이 같은 값으로 묶이면 순서가 매번 달라질 수 있다. 정렬 조건 맨 끝에 등록일 내림차순처럼 결정적인 기준을 두어 순서를 고정한다.
- 같은 의미의 응답 필드는 API 전체에서 이름을 통일한다(예: 등록일은 모두 `created`). 클라이언트 매핑 실수가 줄어든다.
- 콘텐츠 유형을 구분하는 필드(`contentMode` 등)를 응답에 함께 실으면 한 목록 API로 여러 유형을 내려줄 수 있다. 반대로 특정 유형만 보여야 하는 목록은 조회 조건을 명시적으로 고정해야 다른 유형이 섞이지 않는다.
- S3 같은 비공개 스토리지의 리소스 목록을 내려줄 때는 presigned URL을 함께 발급하면 클라이언트가 별도 인증 없이 바로 내려받을 수 있다.
- Spring Security에서 인증 없이 보호된 리소스에 접근했을 때 401이 아니라 403이 나올 수 있다(EntryPoint 설정에 따라 다름). QA·테스트의 기대값은 실제 보안 설정과 맞춘다.
- 에러 메시지는 요청 언어(`Accept-Language`)에 맞춰 다국어로 내려준다. 선택 가능한 목록도 해당 언어로 노출되는 항목만 보이도록 거른다.
- 나중에 원본이 바뀔 수 있는 값(예상 소요 시간 등)은 생성 시점에 스냅샷으로 저장해야, 이후 원본이 수정돼도 기존 데이터가 흔들리지 않는다.
- 외부 시스템 연동 전송을 매분 폴링하던 방식에서 하루 한 번 새벽 배치로 묶어 보내도록 바꾸면, 실시간성이 필요 없는 경우 호출 수와 부하가 크게 줄어든다.
- 새 기능을 넣을 때 정렬·다국어·권한·응답 필드명·QA 페이지 같은 공통 관심사를 확인하는 점검표를 문서로 두면, 같은 종류의 누락이 반복되지 않는다.
